Tests That Prove Nothing

I spent twenty days building an agent that onboards suppliers and then keeps governing them for months. The bugs that mattered were never red. Every one of them shipped under a green suite, and four of the five came from the plan rather than the code.

Five defects, and the discipline that caught them.

A passing test is a claim about your code. A test you have watched fail is evidence. Most of the time the difference does not matter, because most tests are written against code that either works or obviously does not. Autonomous systems break that assumption, and they break it quietly.

The system I was building reads a supplier's certificate, screens the company against a sanctions index, scores the result against a written policy, escalates to a human when the policy demands one, writes to a real ERP, and then wakes up months later to chase the renewal, restrict the supplier if the evidence is overdue, and lift the restriction when it arrives. Agents propose; deterministic code decides; a ledger records. That last part matters more than it sounds like it should.

What follows is five real defects. None of them was caught by a failing test, because in every case the tests were green and wrong. They are grouped by symptom rather than numbered, because they are a taxonomy and not a sequence — you can meet them in any order, and probably will.

symptom: the control was never exercised

A safety eval that measured the model's manners

A document arrives with a sentence planted in it addressed to whatever machine reads the page next. The eval for this passed. I believed I had a working injection defence for about a day.

What the eval actually measured was the model declining to comply. Nothing in the enforcement path had been exercised at all. On a different day, with a different temperature, the same green test would have sat over a system that did the wrong thing.

Worse, the control I thought was doing the work could not have done it. Extracted values are checked against the source document — a value has to appear in the span the agent cites. But an obedient agent cites the planted sentence as its provenance, and that sentence genuinely is on the page. Provenance checking accepts injection-obedient extraction by construction. It is a defence against invention, not against instruction.

The fix was to stop conflating the two. Detection of a planted directive is a separate, deliberately narrow heuristic. Enforcement is exact and structural: a document flagged as tainted is never published to any state key an agent's instruction can resolve, so extraction has nothing to read, and the risk gate is forced to blocked regardless of what any model would have said. The claim I can defend is not "we detect prompt injection" — a rephrased payload gets past the heuristic. It is that a tainted document cannot produce a write.

grade the enforcement outcome, not the model's reply eval was measuring nothing

symptom: both halves correct, jointly inert

An approval system where every part worked and nothing happened

Human approval was specified carefully. One decision per approval id, bound to the exact version of the case the reviewer was shown. A replay is refused as a duplicate. A decision about a version the case has already moved past is refused as stale. The executor independently refuses to perform anything for a case the policy has not cleared. Both pieces had tests. Both pieces were correct.

Together they did nothing whatsoever. The terminal that parked a case for review claimed no work — so when a human approved, the approval and the executor agreed, precisely and correctly, about an empty queue.

This is the failure mode I now watch for hardest, because unit tests are structurally bad at it. Each component's tests passed because each component was right. The tests that appeared to prove the release path built their starting state by hand, and the state they built was one the real system produces only during a rare redelivery anomaly. They tested a shape the system essentially never has.

Nothing failed. I found it by reading the parking code and the approval code side by side and asking what actually connects them. The answer was: nothing did.

make the parking terminal claim what it parks feature existed for the first time

symptom: off-by-one in a comparison, not a count

The audit that asked > 1 and got a clean bill of health

A short one, and my favourite, because the bug is a single character and the consequence was nearly a false gate.

Commands carry a counter that is incremented in exactly one place: the function that records a failed attempt. I wanted to prove the retry path had genuinely happened in production — that some command had failed, been retried, and succeeded exactly once. So I queried for commands with a counter greater than one and a status of done.

Nothing matched, and I briefly concluded the retry path had never once been exercised for real. But a command that failed once and then succeeded has a counter of exactly 1. The correct query was >= 1. One record among forty-eight matched it — a single command that failed, was re-driven by the scheduled sweep, and completed six seconds later, leaving exactly one downstream record behind.

The lesson is not "be careful with comparisons". It is that a field whose only writer is the failure path does not mean what its name suggests, and I should have read that writer before writing a query against it.

the audit query: > 1 becomes >= 1 0 matches → 1 match

symptom: the acceptance criterion is impossible

A proof written to wait for an event the system cannot emit

My own plan told me to verify something that cannot occur. It said: watch a restriction get applied to a supplier whose review was rejected, through the browser, after the rejection.

It cannot be watched, because it has already happened. Restrictions are not withheld pending human approval — only permissive actions are. And the drain that executes pending work runs unconditionally after every invocation, so by the time a reviewer opens the page, the restriction is long since applied.

Measured on the real run: the restriction landed at 18:33:13.987Z and the human decision committed at 18:44:22.401Z. Eleven minutes and eight seconds earlier, not after.

Had I built the proof as written, it would have hung waiting for an event with no producer, and the only way to make it pass would have been to weaken the assertion until it described something else — which is exactly how a suite fills up with tests that pass and mean nothing. I caught it while designing the harness, by reading the drain against the executor before writing a line of it.

The replacement claim is both true and stronger, and it took two server timestamps rather than a screen recording: a rejection withholds the permissive actions; the restrictive one never waited for a human at all.

when a proof will not pass, suspect the claim before the test criterion was unsatisfiable

symptom: a correct consumer of state nobody writes

Reading a field that is null on every record ever stored

This one is from the last week, while building the scoreboard that reports what the system actually did. One metric counts data fields carried into the ERP without anyone retyping them, and the obvious source was the structured extraction the evidence step produces — a list of fields, each with its value and the span it came from.

That list is never persisted. It lives in working state during the run and is written to the record under a different key, in a different shape, holding a summary rather than the fields. On every stored case, the key I was about to read is null.

A metric built on it would have compiled, passed its unit tests against hand-built fixtures, run happily in production, and reported zero forever without ever failing. I found it by opening two real documents and printing their keys before writing the code — three minutes that saved a silently wrong number in a scored artifact.

Read the code that writes the state before you build anything that reads it. A correct consumer of state that is never produced ships inert, and its tests still pass.

print the real document's keys before coding source field is always null

What actually catches these

Three habits, in rough order of how much they earned.

Name the edit that would break each test, then make it

For every test that guards something load-bearing, I write down the specific change to production code that should turn it red — and then I actually apply that change and watch. It takes a minute per test. On the failure-handling work, five tests passed while proving nothing, and mutation caught every one. Four of those five were test code my own plan had specified, which is the part I did not expect: plan code is unverified code, and it arrives wearing the authority of a decision already made.

Every readout strip above is a real mutation with its real outcome. On the metrics module in this article's own system, five mutations — flipping >= to >, dropping the cycle from a write key, ignoring whether a command executed, trusting dates without the writes that back them, and returning 0 instead of null for a missing input — each flip exactly one test red. That is what makes the green meaningful.

Make the summary re-execute its own citations

A table mapping "criterion" to "the test that proves it" is a claim about the repository, and it rots the moment a test is renamed. The exit-criteria manifest re-runs the twenty-two test ids it cites and re-reads each evidence file it points at, every time it runs. A deleted, renamed, or red test demotes its criterion instead of continuing to look satisfied. I mutation-tested the manifest too: renaming a cited test, deleting a file, and removing a downstream record each turned it red.

Accept that some defects need a live run

One bug could not have been caught by any unit test at any coverage level. A platform field that reports how many times a message was delivered is populated only on subscriptions that carry a dead-letter policy. Mine deliberately has none, so the field is empty and the count arrives as a message attribute instead. Every mock returned the number I expected. Only a real message through real infrastructure showed the field blank — the live run measured five where the code would have recorded zero forever.

The pieces worth stealing

Four contracts did most of the structural work. None is clever; all are boring on purpose, which is the point.

  • the event envelopeEvery inbound event carries its own id, the case it belongs to, and optionally the case version it expects. One transaction claims the id, rejects a duplicate, rejects a stale version, and advances the case — or does none of it. That single transaction is the entire boundary between at-least-once delivery and duplicate side effects.
  • the tool surfaceEvery external write is addressed by an id derived from (case, action, cycle). The cycle is in the identity because the lifecycle repeats: the same action in a later cycle is legitimately new work, and without the discriminator the second one silently finds the first marked done and skips. Where the far side deduplicates by deterministic id, redelivery is harmless twice over. Where it does not — outbound mail, which nothing on the far side deduplicates — the ledger is the only guard, and saying so plainly in the code is what keeps someone from assuming otherwise later.
  • the catalog contractAgents are declared with their permitted tools and their permitted routes, and routing narrows against that declaration rather than trusting a model's proposal. A known-but-not-permitted agent is dropped and the drop is recorded; an unknown agent stops the case. The guarantee is narrow and exact: nothing runs unless policy permitted it.
  • the contract-test harnessEvery failure encountered in the build becomes a contract test or an eval case, and evidence for anything gate-shaped is written into the repository next to the code — never to a temporary directory. I learned that one the direct way, by losing a day's proof to a scratch path that did not survive the session.

The uncomfortable part

Every defect here was found by reading, by mutating, or by running the thing for real. None was found by a test going red on its own. If I had trusted the suite, all five would have shipped, and the suite would have been just as green afterwards.

I do not think that is unusual for agentic systems. The components are individually testable and the interesting failures live between them, in the gap where two correct pieces agree about nothing, or where a control is present but never exercised because the model happened to behave. Coverage does not see that gap. Only adversarial reading and deliberate breakage do.

Green is not evidence. Green plus a mutation you watched turn it red is evidence.
